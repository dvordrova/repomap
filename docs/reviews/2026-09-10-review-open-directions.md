## 3. По разделам снимка

### §1–2. Что считать интеграцией, и почему нынешняя правка не дойдёт до адреса

Контракт v3 хорош формой, но два его столбца заполняет модель там, где должен код:

- `destination` это свободный текст до 80 рун. В `151409` модель написала «remote HTTP
  peer» для `Do` и «OTLP trace collector» для экспортёра. Второе поддержано именем API,
  первое это пересказ вида `http_client`. Валидатор это принял; на странице читатель
  увидит «удалённый HTTP-пир», то есть ничего.
- `address_options` строятся `BoundaryAddresses` из литералов вызовов владельца
  (`tables.go`, рабочее дерево): лексическая близость, о чём сам промпт честно
  предупреждает («lexical proximity alone does not connect values»). Для `SendRequest`
  список пуст, потому что адрес приходит параметром `url`.
- Расширение контекста (вызывающие, документация файла, README) даёт модели подсказки к
  смыслу и это правильно, но адрес оно не восстановит: в `NewServer$3` выражение
  `proxyEndpoint+"/hello"` записано в индексе как `dynamic` без частей, а параметров как
  объектов в индексе нет вовсе (`program-facts` прогона: виды объектов function, method,
  type, variable, external_symbol). Три места потери перечислены в разделе 4a основного
  документа; повторю кратко: аргумент только `literal_string|dynamic`
  (`surfacediscovery/external_call_index.go:80`), нет связи аргумента с параметром
  объемлющей функции, нет связи локальной переменной с результатом `flag.String`;
  `facts/http.go:281` требует литеральный путь во втором аргументе; `facts/config.go:47`
  не знает флагов.

**Ответ на «ограничение формы результата» (одна граница = одна destination).** Единица не
физический вызов, а **цепочка назначения**: (место транспортного вызова, разрешённый адрес
или точка остановки, путь через адаптер). У одного `Do` в общем helper столько строк,
сколько различных цепочек в него приходят; общий helper при этом записан один раз как
адаптер, а транспортное свидетельство не дублируется. Это не новый граф: это проход по уже
существующим отношениям `calls` с паттернами аргументов, которым не хватает трёх видов
значения.

#### 4a. Адаптерный слой: как я это вижу (дополнение по просьбе владельца)

Определения, все из существующих фактов:

- **Транспортный вызов**: вызов из закрытой таблицы механизмов обмена (`net/http`
  `Do/Get/Post/NewRequest*`, `database/sql`, gRPC-клиенты, брокеры; Python
  `requests/httpx/aiohttp`, драйверы БД; JS `fetch/axios`, клиенты БД). Таблица уже есть
  для HTTP (`facts/http.go:10-31`), её надо дополнить, а не заменять энциклопедией.
- **Аргумент назначения** транспортного вызова: адрес/URL у HTTP, DSN/строка запроса у БД,
  топик у брокера, endpoint у экспортёра. Виды значения: `literal`; `parameter:k`
  (значение это k-й параметр объемлющей функции); `concat` из частей
  (`parameter:2 + "/hello"`); `call_result:<ref>` (локальная переменная с результатом
  записанного вызова: `flag.String`, `os.Getenv`, `viper.GetString`, конструктор клиента);
  `field:<name>` (поле получателя). Всё это видно в SSA у Go-адаптера (там уже есть
  `ResultID` и `ReceiverResultIDs`), у Python и JS в их AST.
- **Адаптер**: объявление, где транспортный вызов получает аргумент назначения из
  параметра или поля получателя. `utils.SendRequest` в сервисе владельца; тип `Exchange`
  во Freqtrade поверх ccxt; `rafthttp.pipeline` и `streamReader` в etcd. Тип с полем
  базового адреса, назначенным в конструкторе, это адаптер-клиент.
- **Место интеграции**: вызов адаптера с разрешённой цепочкой. Обработчик `GET /proxy`, а не
  `SendRequest`.

Алгоритм (детерминированный, без модели):

1. Для каждого транспортного вызова взять аргумент назначения.
2. `literal` → адрес найден. `concat` → собрать из частей, нерешённые части оставить в
   виде `{parameter:k}`. `parameter:k` → для каждого вызывающего той же цели по отношению
   `calls` взять его k-й аргумент и повторить с шага 2. `call_result` читателя
   конфигурации → адрес это «значение флага/переменной `proxy-endpoint` (по умолчанию
   пусто)», с якорем читателя. `call_result` конструктора клиента → его аргументы по тем же
   правилам. `field` → присваивание поля в конструкторе, дальше как параметр.
3. Границы: не больше трёх прыжков; только внутри цели; не больше пяти вызывающих на
   прыжок; любой другой источник (`picker.pick()`, чтение из карты, значение из ответа
   другого вызова) останавливает проход с честной записью «адрес не установлен: значение
   из `p.picker.pick()` в `pipeline.go:134`». Никакого полного dataflow, никаких догадок по
   именам переменных.
4. Результат: цепочка с якорями каждого звена. Для сервиса владельца: `main.go:17` флаг →
   `main.go:32` → `gen_server.go:32` → `requests.go:22` → `requests.go:31`; итог «GET
   `{--proxy-endpoint}/hello`». Для трейсов: «OTLP по `{--trace-endpoint}`».

Как это ложится в контракт v3: `address_options` получают элементы цепочки (закрытые `a*`
с текстом выражения и якорем), `destination` заполняется кодом там, где цепочка дошла до
литерала или конфигурации, и остаётся свободным текстом только для роли при остановке;
`basis` без изменений; модель отвечает на «зачем» по подсказкам (имя функции, комментарий,
README) и это помечается как интерпретация. Строка на странице: `HTTP →
{--proxy-endpoint}/hello · через utils.SendRequest · из GET /proxy · [код]`. Сто вызовов
`Do` в одном пакете это один адаптер с перечнем операций, которые через него ходят.

Что этим покрывается из проверяемых случаев снимка: 1 (литерал и динамический адрес), 2
(клиент поверх helper), 3 (один helper на разные системы: разные цепочки; одна система из
разных мест: одинаковый разрешённый адрес), 4 (экспортёр: `call_result` конструктора с
`WithEndpoint` из флага; stdout-экспортёр: нет аргумента назначения → не граница), 6
(сборка запроса без отправки: `NewRequest` не в таблице транспорта, отправка это `Do`).
Что не покрывается и честно остаётся «неизвестно»: 5 частично (SQLite/bbolt — локальные
по таблице драйверов, это закрытый список, а не догадка), адрес из `picker.pick()` в etcd
(«пир из списка членов кластера» появится только если роль поддержана заголовками
`X-Raft-To` и документацией, как в baseline), Python `self._url` из вложенной
конфигурации (`config['webhook']['url']` это `call_result` чтения конфигурации с ключом,
если чтение записано как наблюдение; иначе остановка на поле).

Чего не делать: не просить модель угадывать адрес по README; не считать число вызовов
числом систем; не склеивать разные цепочки по одинаковой роли «peer service»; не
объявлять каждый wrapper адаптером без транспортного вызова внутри.

### §3. Воркеры

Снимок прав, что «имя `run` и наличие `for` недостаточны». Но у Freqtrade все три потери
имеют детерминированный источник, которого нет в фактах:

- `ExchangeWS.__init__` запускает `Thread(target=self._start_forever)`
  (`exchange_ws.py:34-35`). Это регистрация потока, а не «привязка callable к полю»; в
  строке она превратилась в `self._start_forever -> _start_forever` без смысла `Thread`.
  Нужен факт «запуск потока/задачи»: `threading.Thread(target=)`, `asyncio.create_task`,
  `loop.run_forever`, `multiprocessing.Process`, у Go оператор `go` (уже есть), у JS
  `setInterval`/`Worker`. Это тот же класс, что goroutine.
- Расписания: `freqtradebot.py:159-175` регистрирует периодические задачи, принято ноль
  `scheduled`. Регистрации в планировщике (`schedule`, `apscheduler`, cron-декораторы,
  `time.AfterFunc`, `Ticker` внутри цикла) это факты, модель должна получать их как
  наблюдения с якорем, а не выводить из имени.
- `lifespan` FastAPI принят как continuous. Это хук жизненного цикла сервера
  (регистрация), отрицательный факт того же рода, что «test setup/teardown это не
  расписание» в промпте.

Порядок диагностики из снимка (извлечение → строка → решение → проекция → HTML) верный;
для этих трёх случаев первое место потери это извлечение.

Три формы запуска одного бота (`freqtrade.main`, `python -m freqtrade`, `freqtrade`) с
одинаковыми 172 входами и 604 исходящими это не «одинаковые операции у Python-целей», а
одно приложение с тремя точками запуска: main guard, `__main__.py`, console script в
`pyproject.toml:143` ведут в одну функцию `main()`. Для portfolio это положительное
свидетельство `seed_of`: одинаковая функция запуска. Считать ниже, что это стоит.

### §4. HTTP-пути

- `facts/route_prefix.go` собирает префиксы только для chi (`nestingSelectors: route,
  mount`). FastAPI `include_router(router, prefix="/api/v1")`, Flask
  `register_blueprint(url_prefix=)`, Express `app.use("/api", router)`, Django `include()`
  это тот же механизм с другими именами. Расширение таблицы, не новый анализ. Freqtrade
  `/ping` → `/api/v1/ping` должен появиться из этого.
- Python-декоратор не попадает в каталог `p*`, потому что каталог строится из callback
  bindings. Факт `http_route` для того же объявления уже есть (`facts/http.go`); его надо
  подать как `registered_names` по идентичности объекта. Снимок это признаёт, добавлю
  критерий: в игре модельный путь для `get_levels_info` должен быть ровно `/api/levels`
  или отсутствовать, а не `GET /levels`.
- Airflow 120 из 222: считать по файлам с декораторами и нулём фактов, как записано в
  основном документе.

### §5. Промпты и валидация

Кроме сверки в §2: `destination` «remote HTTP peer» это новая форма старой проблемы
«`Do` выполняет HTTP». Пока цепочка не реализована, странице лучше показывать `basis` и
`address: unknown` как «адрес не установлен», а роль выводить только если она не
синоним вида. Это правило показа, не переписывание решения.

Терминологические отказы никуда не делись: в `151409` `rejected.jsonl` содержит
`terminology_metadata_rejected` в documentation_reduce, symbols, operations, joints, learn,
orientation («misplaced optional terms field», «missing optional terms array», «term has
no source-backed occurrence»). Это шум в журнале и лишний выход; решается тем же, что и
зацикливание в §6.

### §6. Learn, вопросы, ответы

Зацикливание словаря (128 000 выходных токенов, 318 с, 3 733 строки терминов при 129
именах) имеет две причины, и обе не в промпте:

1. Необязательный придаток генерируется **внутри** того же ответа, что и результат.
   Дедупликация «локально» не помогает: повтор происходит при генерации, деньги уже
   потрачены. Для прозаических таблиц вынести термины из конверта: отдельный дешёвый
   проход по принятой прозе (сводный этап glossary уже есть) либо жёсткий предел числа
   терминов в контракте ответа. Это не «молчаливое переписывание решения»: термины это
   метаданные, не решение.
2. Полка вывода 128 000 токенов резервируется независимо от ожидаемого размера. Ответ
   Learn это 7 КБ; при пределе 16 000 токенов зацикливание умерло бы за секунды и
   несколько центов, и одновременно освободилось бы ~100 тыс. токенов контекста.
   **Поправка после ответа исполнителя:** резерв объясняет только отказ Learn Freqtrade
   (1 005 903 + 128 000 при окне 1 048 576: без резерва вход помещается); отказ retrieval
   Webernetes (1 191 943 входа) не объясняется, там вход сам больше окна, и нужна
   упаковка входа по измеренному порогу из следующего абзаца. Предел вывода и порог
   упаковки делать вместе. Предел вывода по стадии, привязанный к ожидаемому результату,
   это не «произвольный лимит по одной цифре», это размер ответа, который контракт сам
   определяет.

Retrieval: в одном дочернем окне на ~600 тыс. токенов модель пропустила 60 из 64 строк
вопросов; в Go-запросе на 8 тыс. токенов пропусков ноль. Это измерение надёжности
упаковки, а не квота: нужен тест «доля пропущенных строк от размера запроса» на
сохранённых входах и порог упаковки, при котором пропусков нет. Снимок против
произвольных квот, и я тоже; порог из измерения это не произвольная квота.

### §12. Данные и SQL (вопрос 6 и мысли владельца)

Владелец: «поиск SQL отдельный… звучит как вопрос классификации LLM, типа вот это вызов к
БД кажется» и «обратный путь: нашли SQL → разбираем → ищем вызывающий код». Моя позиция:
классификация «это обращение к БД» на девять десятых детерминированная, модель нужна для
остатка и для назначения.

Что есть: `extractors/sqlc.go` читает конфигурацию sqlc и связывает объявленные файлы
схем и запросов; разбора SQL, инвентаря таблиц и связи «вызов → запрос → таблица» нет.

Минимальный полезный результат, в порядке:

1. **Источники схемы** (детерминированно, с природой источника): миграции и `*.sql`
   (`CREATE TABLE`, колонки, PK/FK), sqlc (уже есть), ORM-модели (SQLAlchemy
   `__tablename__` и `Column`, Django `Meta.db_table`, GORM теги, Prisma, TypeORM). Каждая
   таблица с якорем и пометкой «миграция / модель / упомянута в запросе». Разные соединения
   и схемы это разные объекты.
2. **Запросы** (детерминированно): литералы SQL в коде (строка, начинающаяся с
   `SELECT/INSERT/UPDATE/DELETE/WITH/CREATE`, включая f-строки и конкатенацию с частями
   `{параметр}`), файлы запросов sqlc, `sqlalchemy.text(...)`. Для каждого: вид оператора,
   упомянутые таблицы и колонки (терпимый разбор: `FROM/JOIN/INTO/UPDATE` плюс полный
   парсер там, где диалект известен), исходный SQL и якорь. Динамический SQL даёт
   частичный набор имён с пометкой «частично».
3. **Обращения к БД без SQL** (детерминированно по таблице клиентов, как у HTTP):
   `session.execute/query/select`, `cursor.execute`, `db.Query/Exec`, `gorm.Find`,
   `prisma.user.findMany`. Это тот же адаптерный проход из 4a с аргументом назначения
   «запрос или модель». Строитель запросов без отправки это не обращение.
4. **Связь в обе стороны через существующий граф**: вызов → метод доступа → запрос →
   таблицы; и обратно: SQL → объявление, в котором он лежит → вызывающие → операции.
   Обратный путь дешёвый, потому что отношения `calls` уже есть.
5. **Модель**: одна фраза назначения на запрос («читает открытые сделки пары для
   проверки лимита позиций») по имени функции, параметрам, комментариям, и классификация
   только для действительно неоднозначных обёрток (`client_get` во Freqtrade). Помечается
   как интерпретация. Никаких «хранимых процедур» и колонок, которых нет в источниках.
6. **Показ**: полка «Данные» на входе компонента: таблицы (источник природы), запросы
   (вид, таблицы, якорь), переходы таблица ↔ запросы ↔ операции. «Известны только
   упомянутые объекты» пишется прямо, когда схемы нет.

Приёмка на Freqtrade: модели в `freqtrade/persistence/models.py` (сделки, ордера,
блокировки пар, ключ-значение) с колонками из `Column`, 20 использований
`sqlalchemy.text` в миграциях как запросы с таблицами, `select()` в персистентности как
обращения без SQL-строки, связь «`GET /trades` → `Trade.get_trades` → таблица `trades`».
Контрпримеры из снимка: одинаковое имя таблицы в двух соединениях, `JOIN` без FK,
частичный динамический запрос.

## 5. Ответы на семь вопросов §15

1. **Определение результата.** Достаточно, если единица это цепочка назначения, а не
   физический вызов: участник (роль или разрешённый адрес), назначение (интерпретация по
   подсказкам, помечена), контекст использования (место интеграции), транспортное или
   конфигурационное свидетельство (адаптер и его вызов). Общий helper с несколькими
   назначениями это один адаптер и несколько цепочек; представляется без нового графа
   проходом по `calls` с тремя новыми видами аргумента (§4a).
2. **Первое место потери** для существенных дефектов: адрес исходящего — индекс
   (аргументы `literal|dynamic`, нет параметров, нет частей); воркеры Python — извлечение
   (нет факта запуска потока и регистрации расписания); пути FastAPI — факты
   (`route_prefix.go` только chi; маршрут не подан в `registered_names`); модельный путь
   `GET /levels` — подготовка запроса (свободный `name` без каталога); зацикливание Learn
   — конверт ответа и резерв вывода; троение joints — отсутствие мемо по содержанию и
   лишние цели; `remote HTTP peer` — валидация/показ (принят пересказ вида).
3. **Неверные решения против разумных интерпретаций.** Неверные: `Sleep`, регистрации и
   YAML как интеграции (закрыто), `lifespan` как continuous, `GET /levels`, три
   приложения из одного бота, «Run worker loop» как ответственность. Разумные с
   ограниченной уверенностью: «OTLP trace collector», «Establishes an HTTP streaming
   connection to a peer», «Posts a data payload to a URL» (верно, но без смысла, потому
   что смысл лежал в `handle`). Нейтральные факты, которые языковой слой должен знать
   заранее и которые не являются энциклопедией stdlib: происхождение вызываемого (индекс /
   платформа / пакет, уже есть `authority_kind`), виды аргумента назначения (§4a),
   закрытые таблицы транспортных и конфигурационных API по языку (по 10–20 имён),
   запуск потока/задачи/goroutine и регистрация в планировщике, контекст управления (есть),
   регистрации роутеров и их префиксы, закрытый список локальных пакетов (`time`, `sync`,
   `fmt`, `strings`, `encoding/*`, `context`, `log`), которые не предлагаются как
   кандидаты обмена. Всё остальное интерпретация с пометкой.
4. **Порядок** — §6 ниже.
5. **Спорные пункты.** Сверка в §2: четыре опровержения приняты, два частично, три
   замечания остаются с уточнением. Дополнительно опровергаю одно утверждение снимка:
   «Ошибка здесь прежде всего в понимании роли шагов, а не в отсутствии удаления дублей»
   верно для OTel, но для `Do` ошибка не в понимании, а в отсутствии данных: без цепочки
   модель не может знать адрес, сколько контекста ей ни дай.
6. **Обзор таблиц и SQL** — §3 к разделу 12.
7. **Достаточно / до большого запуска / отложить.** Достаточно: контракт границ v3 по
   форме, `When`, отбор без ложных исходящих, компактный первый экран, ответы с
   источниками, перевод. До следующего большого запуска: предел вывода по стадии; одна
   цель на формы запуска; мемо joints; цепочка назначения хотя бы для Go и HTTP; факты
   маршрутов в `registered_names` и префиксы FastAPI; факты потоков и расписаний Python;
   решение о тестах в обзорном виде. Отложить: markdown-книга, связь репозиториев,
   структурный рефакторинг, полный обзор данных (после первого шага со схемой и sqlc).

## 6. Порядок работ с критериями приёмки

1. **Предел вывода по стадии** (`max_tokens` из ожидаемого размера результата; Learn и
   retrieval в первую очередь). Критерий: повтор дочернего Learn Freqtrade на
   сохранённом входе не превышает 16 000 выходных токенов и не отказывает по контексту при
   том же входе. Стоимость: часы.
2. **Одна цель на формы запуска** (portfolio: одинаковая функция запуска → `seed_of`).
   Критерий: Freqtrade даёт одну карточку бота с тремя строками запуска, число живых
   запросов joints падает не меньше чем на 84 при том же входе.
3. **Мемо joints по содержанию.** Критерий: на том же входе нет двух живых запросов с
   одинаковыми `a` и peers.
4. **Цепочка назначения** для Go и HTTP (три вида аргумента, проход с границами).
   Критерий: на сервисе владельца `address` для `Do` это `{--proxy-endpoint}/hello` с
   пятью якорями, для экспортёра `{--trace-endpoint}`; на etcd `pipeline.post` даёт
   «адрес не установлен: `picker.pick()` :134» и роль пира из заголовков; bbolt не
   граница. Потом Python (`requests.post(self._url)` → `config['webhook']['url']`) и JS.
5. **Факты маршрутов и префиксов**: `http_route` в `registered_names` по идентичности
   объекта; `include_router/register_blueprint/app.use` в `route_prefix.go`. Критерий:
   игра даёт `/api/levels` и никаких модельных путей; Freqtrade даёт `/api/v1/ping`;
   Airflow не меньше 120 и считается по файлам с декораторами без фактов.
6. **Факты потоков и расписаний** Python/JS. Критерий: `_start_forever` и
   `_continuously_async_watch_ohlcv` приняты как continuous, три задачи из
   `freqtradebot.py:159-175` как scheduled, `lifespan` не continuous; контроль: bounded
   retry в webhook и конечный цикл `_schedule_while_true` не воркеры.
7. **Показ неизвестного адреса и роли** (правило страницы). Критерий: строка исходящего
   без адреса читается «HTTP → адрес не установлен · через X · из Y», роль-синоним вида не
   печатается.
8. **Термины вне конверта для прозаических таблиц** либо жёсткий предел числа терминов.
   Критерий: ноль `terminology_metadata_rejected` в `rejected.jsonl` трёх прогонов.
9. **Уборка формы**: одиночная привязка без `rows:[null]`; `scope` один раз в контексте;
   `outbound` не спрашивается при пустых `call_options`. Критерий: перерендер на
   сохранённых входах, счётчики ноль, принятые решения на тех же ответах не меняются.
10. **Решение о тестовых рёбрах и частях в обзорном виде**; затем UI-приёмка по критериям
    раздела 5 основного документа на Webernetes, игре и Freqtrade.
11. **Данные и SQL**: шаг 1–2 из §12 (схема из миграций/ORM/sqlc, запросы-литералы с
    таблицами), связь через граф; модель только для назначения. Критерий: Freqtrade даёт
    таблицы из `persistence/models.py` и связь `GET /trades → trades`.
