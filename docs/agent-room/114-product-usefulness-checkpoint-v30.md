# Decision: Repomap v3.0 Product Usefulness Checkpoint

Status: Approved by the repository owner in the current implementation
session.

## Product outcome

Evaluate the normal repomap product as an unfamiliar-repository onboarding
workspace. On a genuinely fresh frozen Litestream run, automatically discover
one central, source-backed behavior; explain it in human action phases; connect
it to exact code, useful next targets, Search, and distinct architecture
context; and preserve useful chi and Caddy fixtures. Correctness remains
necessary but peripheral/easy-to-prove output is not a successful result.

The untracked checkpoint contract at `tmp/repomap-v30/PRODUCT_CONTRACT.md` was
fixed before production code changed and is the operational product-evaluation
contract for this decision.

## Approved implementation scope

1. Extend the existing bounded opportunity candidate, without introducing a
   new truth object, to carry a natural question, kind, target user job,
   central anchors, expected input/core/effect, architecture areas, required
   and available evidence capabilities, bounded frontier, onboarding and
   investigation rationale, and estimated cost.
2. Validate candidate fields and opaque references locally. Select candidates
   locally with separately retained scores for evidence readiness, purpose
   alignment, explanatory value, navigation value, and penalties. `Start Here`
   must clear purpose, explanation, navigation, and correctness requirements;
   evidence availability alone cannot make it primary.
3. Reuse the existing candidate-specific bounded evidence planner with no more
   than three candidates, two frontiers per candidate, eight files, fifteen
   functions, depth three, 128 KiB retained source, five seconds of local work,
   one synthesis call per eligible candidate, and no semantic retry.
4. Require a natural retained question, an answer that addresses it, at least
   three meaningful actions, concrete code for every phase, an immediately
   visible input/core/effect, more than one trivial local operation, purpose
   alignment, and two to five exact next files or symbols before a mechanism is
   eligible as primary.
5. Add a presentation-only `RepositoryGuide` projection over already accepted
   orientation, architecture, and Mechanism v1 artifacts. It may organize
   repository purpose, areas, one `Start Here` mechanism, an extension section,
   more paths, read-next targets, Search, and Architecture. It does not create
   claims, support, ordering, facts, or semantic identity.
6. Add presentation-only three-to-six-phase narrative compression and compact
   multi-fragment source projection. Every action promised by a phase must be
   visible in exact supporting ranges without opening the full function.
7. Keep Architecture only when it contributes distinct responsibility context,
   and preserve focused navigation back to the originating mechanism phase.
8. Keep Search limited to accepted published content and exact mechanism,
   phase, symbol, path, and component routes. Validate natural, domain,
   extension, Russian, path, and symbol queries generically rather than adding
   fixture-specific aliases after failures.
9. Exercise normal CLI forms for the current directory and an explicit path,
   along with `--no-open`, `--no-search`, and `--no-serve`. The main demo must
   use the normal production path, serve on `127.0.0.1`, open Overview when
   allowed, and print the exact review URL.
10. Run one genuinely fresh production analysis of Litestream revision
    `d26cb54ec43b5937a0c8b3bd875696c1375d8cb3`. Do not reuse earlier questions,
    candidate roles, manual windows, seeds, final responses, or contracts.
11. Preserve the chi request-dispatch library fixture and Caddy directory-
    listing application fixture, including supported content, exact source
    navigation, and semantic identities/hashes.
12. Save the prescribed untracked `tmp/repomap-v30/` review bundle, product
    scorecard, walkthrough, future-readiness note, and screenshots. Automated
    checks do not satisfy the owner blind-review gate; its status remains
    `awaiting_owner_review`.

## Model-call contract

The fresh Litestream run may use bounded structured calls for opportunity
planning, up to three candidate syntheses, an optional repository-thesis
editorial pass, and optional narrative compression. Every semantic leaf is
based on repository facts rather than another model summary. Responses are
locally validated, no semantic retry is permitted, and presentation projections
cannot become truth authority.

## Explicit non-goals

- No runtime-surface discovery, global SSA, repository-wide call graph, pointer
  analysis, or other new global analysis.
- No provider change, second frontend/renderer, universal knowledge-object
  layer, DependencyUsage, ContributionRecipe, MCP, embeddings, runtime Q&A, or
  change-impact implementation.
- No fixture-specific terms, paths, symbols, questions, ranking rules, aliases,
  validators, manual primary selection, response editing, or weakened truth
  contract.
- No claim of complete repository behavior or completed human review.
- At most one small generic deterministic enrichment, only if it is bounded,
  release-blocking, and covered by cross-repository regressions.

## Stop conditions

Stop and report the checkpoint as unsuccessful when the fresh result is only
setup/helper/error/logging behavior, lacks a meaningful repository
responsibility or visible effect, requires hardcoding/manual selection/global
analysis, hides a promised effect outside the primary source projection, or
when architecture adds no distinct context. Do not compensate with UI polish,
longer prompts, retry, manual evidence, or a more attractive hand-written
question.

## Acceptance

The checkpoint is complete only when the normal production path creates a
fresh Litestream report and review bundle, `Start Here` is central and
source-complete, Search and exact navigation work, chi/Caddy regressions remain
useful and stable, technical checks pass, all product dimensions are scored
separately, and the final served review is left explicitly awaiting the
repository owner's blind review.
