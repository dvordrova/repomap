## Problems proven by the linked product review

1. The ordinary command printed `Run: ready` after any generated report, while
   the corpus harness printed `PASS` after merely reading `report.json`.
   Partial, rejected, failed, unavailable, corrupt, and HTML-missing
   publications could consequently look equally green.
2. One optional source-expansion read failure could terminate the whole Study
   instead of closing only that requested item and retaining valid siblings.
3. Map entry ownership, association labels, mobile fallback, and long inspector
   symbols could contradict the exact current product evidence or make the
   primary Map unusable.
4. D242 correctly removed competing first-hop authorities, but a sibling
   fan-out from one entry is not a mechanism: it proves no continuation,
   causal sequence, or connected vertical through repository work. A separate
   Mechanisms card wall made this naming error more prominent.
5. Study already owns direct readings that identify where a deeper question is
   useful, and the existing Go SSA pass already owns exact static callees. The
   missing product is a bounded, card-local investigation over that evidence,
   not another whole-repository graph build or a model-selected Navigator.

## A. Publication, source-item, and Map truth

### Verified publication state

1. One closed classifier is shared by the ordinary final console and corpus
   harness:

   - `FAILED`: report, current manifest, report binding, or bounded HTML shell
     is absent or invalid;
   - `DEGRADED`: the publication is valid and useful, but an enabled
     Architecture or Study stage is failed, unavailable, partial, empty, or
     incomplete;
   - `READY`: the publication is valid and every enabled semantic stage is
     complete. An explicitly requested offline stage is disabled, not degraded
     merely because no provider call was requested.

2. Existence of `report.json` is never success. Current manifest verification
   and a bounded regular `report.html` application shell are required before
   `READY` or `DEGRADED`.
3. Corpus output persists the closed state and bounded reason codes, records a
   missing matrix repository as `FAILED`, and exits unsuccessfully when any
   publication fails integrity.
4. Human-readable explanations remain in the console. No raw failure, status
   banner, validation code, path, or diagnostic counter is added to HTML.

### Item-local source closure

1. A failed optional source expansion closes only that exact requested source
   with an existing bounded closed reason. Valid siblings continue into
   Adjudication.
2. Mandatory secret scanning, request binding, artifact integrity, and unsafe
   persistence remain terminal. Item-local closure is not general error
   swallowing.
3. The console explains the bounded closed-source count. HTML retains only the
   useful accepted reading material and calm typed frontier.

### Current Map truth fixes

1. Component entry context uses exact owned and participating Surface identity;
   it cannot publish “no entry” while an exact participating process-entry
   Surface or attached process-entry anchor exists.
2. Only typed boundary/resource associations enter the Integrations resource
   presentation. Generic operation/surface rows cannot masquerade as
   resources.
3. At the mobile breakpoint that hides the canvas, the component list is the
   visible default Map representation. Long exact symbols wrap inside the
   inspector rather than creating a nested horizontal viewport.

## B. D210 is Entrypoint handoff context, not a Mechanism

### Backend contract

1. `ArchitectureGrounding.EntryHandoffs` from D210 is the sole first-hop
   authority. Every handoff must match exact process-entry identity,
   declaration location, and scenario. Generic Canvas `behavior_handoff`
   structural edges never create or extend an entry-handoff group.
2. `ArchitectureCanvas.entry_handoff_groups` contains one deterministic
   `EntrypointHandoffGroup` v1 for each exact process entry with at least one
   matched D210 handoff. A zero-hop entry remains first-class in Entrypoints
   and receives no invented group.
3. Each handoff carries its exact D210 relation ref, closed scenario, and typed
   public-safe producer provenance. A readable concatenated evidence string is
   presentation copy only and is never restoration authority.
4. Transition ownership is backend-owned and exact:

   - `entry.component_ids` is the sorted, deduplicated set of accepted
     non-remainder components that contain the exact entry members;
   - every `entry_handoffs[].component_ids` is the sorted, deduplicated set of
     accepted non-remainder components whose declaration identity and location
     exactly match that callee;
   - an unjoined or external target publishes `component_ids: []`;
   - `group.component_ids` may remain the sorted union for accounting, but it
     never replaces per-transition ownership.

5. A missing declaration join never becomes a guessed path, symbol, component,
   or JavaScript join. Input permutation cannot change group identity or
   transition order.

### Entrypoints overlay

1. Entry-handoff groups belong to the Entrypoints lens. Selecting an entry
   draws its exact direct handoffs as an overlay on the existing Canvas using
   only the transition-level component IDs.
2. A cube-to-cube arrow requires exactly one entry component and exactly one
   target component. A missing endpoint remains readable in compact off-map
   overflow. A plural endpoint highlights every exact participant but stays in
   the side lane as ambiguous; it never becomes a sorted-first choice or a
   Cartesian set of invented component relations.
3. There is no Map Mechanisms lens, separate mechanism card wall, or duplicated
   below-map disclosure for D210 first hops. Landscape structural edges retain
   their separate connectivity meaning.
4. The overlay states first-hop truth only. Sibling calls are not chained,
   display order is not runtime order, and the explicit frontier says that
   continuation is unproven.

## C. True Study investigation

### Product result

1. A Study card may acquire one bounded `StudyInvestigation` tied to one or
   more of that card's direct readings. The product publishes plural candidate
   mechanisms inside Study; it does not choose one repository action, recreate
   Navigator, or add an empty top-level lens.
2. The only closed outcomes are:

   - `mechanism`: the model-proposed refs restore to an exact connected simple
     directed path containing at least two consecutive direct-static edges and
     at least three nodes, tied to at least one direct reading;
   - `prepared_investigation`: exact bounded evidence and frontier are useful,
     but no candidate satisfies that proof floor.

3. A lone first hop, sibling fan-out, disconnected subgraph, dynamic invoke,
   or model prose without the complete exact path is always
   `prepared_investigation`, never a Mechanism.

### Private exact call substrate

1. Reuse the private `DirectCallIndex` produced from the existing build-selected
   Go SSA program. Do not load packages again, rebuild whole-repository SSA, or
   introduce CHA/VTA/pointer-analysis reachability.
2. The index admits only repository-local functions and unique call edges for
   which `call.Common().StaticCallee()` returns an exact repository-local
   target. A nil static callee, dynamic dispatch, closure ambiguity, or external
   callee becomes typed frontier, not an inferred edge.
3. One in-memory index is bounded to 65,536 exact repository nodes and 262,144
   unique direct-static edges. Crossing either ceiling clears the whole index
   and makes it `unavailable` with closed reason `node_limit` or `edge_limit`;
   a partial graph is never published or sent.
4. The index is deterministic under input permutation and bound to build
   scenario, repository revision/freshness, producer version, and SHA-256.
5. Closed per-caller counts for dynamic/interface calls, indirect non-static
   calls, and external static callees are part of that digest. A bounded card
   receives only the counts owned by its selected exact nodes; global counts
   are never copied onto every card and no excluded target is guessed.

### Provider-free bounded compiler

1. The production Study adapter compiles only from accepted Study direct
   readings: at most eight final Study cards and at most five primary/direct
   readings per card. The owner-authorized small-repository experiment may
   instead compile one or more caller-supplied exact entrypoint/function
   locators. This explicit-root seam makes no Scout or Adjudication call and
   performs no root discovery, selection, ranking, suffix match, or fuzzy
   repair. Both adapters feed the same bounded graph compiler and validator.
2. Around every resolvable reading, collect the final advertised graph at
   directed distance at most two in each direction. Retain at most eight exact
   neighbors of each reading root per direction, then at most eight neighbors
   per retained depth-one node in that same direction, using balanced
   deterministic round-robin selection. The separate root budget keeps a
   canonically early helper edge from hiding the core fifth or sixth first hop;
   the 32-node/48-edge card ceilings still prevent one high-degree reading from
   consuming an unbounded request.
3. One shallow card bundle is bounded to 32 nodes and 48 edges. Frontier must
   account for every omitted or unsupported branch. Provider-free Air
   calibration fixed the continuation bound at eight: four retained
   `Run -> start` but omitted exact `start -> buildRun` while using only 22
   nodes/24 edges; eight retained both goroutine edges plus `runRule`, used 26
   nodes/32 edges and 4,861 canonical request bytes, and reduced
   `shallow_bound` from eleven to three without a provider call. Filling all
   remaining card capacity is not a goal and would add unproven branch noise.
4. Provider-visible identities are short request-local `t*`, `r*`, `n*`, and
   `e*` refs plus the catalog SHA/ref. The full DirectCallIndex, canonical Atlas
   IDs, raw repository edge set, unadvertised paths, and source bodies never
   enter a request.

### Direct bounded model interpretation

1. The model receives only the final advertised exact graph objects and
   directly returns zero or more plural connected mechanism candidates for
   each context card. One candidate contains only two to eight advertised
   `edge_refs`; model labels, explanations, reading refs, salient node refs,
   endpoint copies, scores, and ranks are not response fields.
2. The model cannot create a node or edge, reverse an edge, establish runtime
   execution, or supply graph order or user-facing prose. Edge-ref order is
   ignored; the backend reconstructs direction, connectivity, every reading
   root on the path, exact invocation display, and calm path text from indexed
   authority. Unknown, duplicate, disconnected, and otherwise invalid refs
   close item-locally.
3. The response is always a plural candidate set, never one chosen repository
   action or root. It contains the smallest useful coherent unordered set of
   zero to three distinct paths, not one item per mechanically qualifying
   helper/logging/default/environment branch. Candidate array order has no
   meaning: the backend validates all items before applying the set bound,
   deduplicates and canonical-sorts accepted paths. More than three unique
   valid paths closes that card as `prepared_investigation` with `over_bound`;
   it never lets the first three win. Invalid siblings remain item-local.
4. One request batch contains at most four cards, 128 nodes, 192 edges, and
   64 KiB of canonical JSON. The owner explicitly authorizes up to four
   separate semantic calls for bounded experiments on small repositories,
   with no semantic retry or response-driven prompt mutation. The shared HTTP
   transport may replay the exact same immutable request bytes after a
   retryable network error under its existing bounded policy. Provider-free
   index construction, compiler tests, and real size/coverage measurement
   happen first as implementation sequencing, not as a permanent no-provider
   policy.
5. There is no model-selected deepen root, next action, or follow-up graph
   expansion. The request already contains the complete bounded graph the
   model may cite; the backend only restores and validates returned refs.
6. One final card is bounded to the same 32 nodes and 48 edges advertised in
   its request, three qualifying mechanism paths of at most eight edges each,
   and sixteen aggregated frontier records. The backend validates every
   candidate against that final exact graph and derives path and result order
   solely from directed authority.
7. Closed frontier values are:
   `no_exact_function`, `unsupported_reading_kind`, `dynamic_invoke`,
   `external_callee`, `shallow_bound`, `depth_bound`, `index_unavailable`, and
   `response_invalid`. Raw codes and operational warnings remain out of HTML;
   accepted user-facing limitations are rendered as calm documentation.

### Binding and coexistence

1. Every investigation identity binds at least its closed context kind and
   context SHA-256, `direct_call_index_sha256`, build scenario, repository
   revision/freshness, and the exact request/result contract versions. The
   Study adapter additionally binds `study_themes_sha256` and
   `atlas_study_catalog_sha256`; the explicit-root experiment must carry no
   fabricated Study authority.
2. `prepared_investigation` and `mechanism` are sibling states of the same
   Study-card contract. Preparation is retained when useful; it never creates
   an empty Mechanisms lens. A later valid mechanism replaces neither the
   original readings nor their frontier.
3. Facts, model candidates, locally validated paths, frontier, and publication
   state remain distinct hash-verified records. Provider prose cannot become
   graph authority.

## Boundaries

- no Canvas structural-edge fallback for entry handoffs or Study mechanisms;
- no second package load or whole-repository SSA rebuild;
- no dynamic-call, CHA, VTA, name, package, or source-prose edge inference;
- no model-created or model-ordered graph truth;
- no Navigator-like single choice, next action, or one-root repository story;
- no new top-level Mechanisms lens or D210 card wall;
- no semantic retry or request beyond the explicit card, graph, byte, and
  four-call experiment ceilings; byte-identical transport replay remains the
  shared bounded HTTP policy;
- no warning, diagnostic archaeology, raw frontier code, or operational
  failure prose in `report.html`.
