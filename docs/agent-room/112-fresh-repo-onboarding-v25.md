# Decision: Fresh Repo Onboarding v2.5

Status: Approved by the repository owner in the current implementation
session.

## Product outcome

The ordinary `repomap` report starts with a bounded repository thesis and a
compact projection of the existing architecture, then distinguishes a central
behavior path from useful secondary and extension mechanisms. Accepted
canonical statements may be compressed into fewer presentation-only narrative
phases without changing their semantic identity or support.

The fixed evaluation target is the untouched `benbjohnson/litestream` checkout
at revision `d26cb54ec43b5937a0c8b3bd875696c1375d8cb3`. Production behavior,
questions, paths, symbols, package names, titles, roles, and architecture must
remain repository-generic.

## Approved implementation scope

1. Reuse the v2.4 deterministic snapshot, orientation, architecture, saved
   source windows, bounded syntax probe, local semantic reducers, Mechanism v1,
   Search, source experience, and report server.
2. Add a presentation-only `RepositoryThesis` derived from documented purpose,
   deterministic census, existing validated architecture, entrypoints,
   boundaries, accepted mechanisms, and exact local navigation targets.
3. Classify accepted mechanisms with a presentation-only onboarding role. A
   local selector, not model prose, owns the canonical role and Start Here
   choice.
4. Rank primary candidates by purpose alignment, core-area and boundary
   coverage, input-to-effect coverage, evidence readiness, and bounded cost,
   with explicit penalties for helper-only, error-only, and registry-only
   topics.
5. When no accepted primary behavior exists, investigate at most two further
   high-centrality candidates. Candidate inputs may be enriched only by bounded
   deterministic reads of already selected entrypoint/core/boundary files.
6. Keep each candidate within eight files, fifteen functions, three expansion
   levels, 128 KiB retained source, five seconds of local probe time, and at
   most two named-frontier follow-ups. Use at most one synthesis call per
   candidate and no semantic retry.
7. Add presentation-only `NarrativeCompression` that groups accepted statement
   IDs into three to six human phases. Local validation must preserve every key
   aspect and member statement reference; it must not create claims, support,
   relations, or runtime order.
8. Use at most one bounded model call for thesis/editorial wording. Every
   returned reference is an opaque supplied ID and is resolved locally. Failure
   falls back to deterministic thesis, roles, and uncompressed accepted steps.
9. Extend the existing User Report only: thesis-first Overview, compact existing
   architecture, role-aware mechanism cards, narrative phases, implementation
   details, and a working return from Architecture to the exact mechanism step.
10. Preserve the accepted Litestream registry Mechanism identity and present it
    as an extension/secondary path even when a central mechanism is found.
11. Save the experiment and review material under the untracked
    `tmp/fresh-repo-onboarding-v25/` directory.

## Explicit non-goals

- No runtime-surface discovery, global SSA, call graph, pointer analysis, or
  repository-wide lifecycle analysis.
- No changes to Mechanism v1 truth, statement support, verdict derivation,
  semantic hashes, Search ranking, providers, or models.
- No Litestream-specific production rule, question, alias, path, symbol,
  package, title, role, or validator exception.
- No DependencyUsage, MCP, private-repository support, new frontend, or general
  UI polish outside the approved onboarding projection.
- No semantic retry or post-response repair of a rejected central candidate.

## Acceptance

Repository Thesis and primary Mechanism are scored separately. The Litestream
Thesis must provide a useful input-to-core-work-to-effect mental model and exact
code-area navigation. A published primary mechanism must explain the
documented core responsibility with at least three meaningful supported
phases. If no bounded central candidate is accepted, the report must honestly
show the Thesis and architecture without promoting a secondary mechanism, and
the negative result remains part of the supervisor review.
